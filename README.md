## 용어 정리

**스프링 컨테이너(Spring Container)**: 자바 객체의 생성, 의존성 주입, 생명 주기 관리를 수행한다.

**스프링 빈(Spring Bean)**: 스프링 컨테이너에 의해 관리되는 재사용 가능한 자바 객체이다.

## 컴포넌트 스캔

각 계층에 맞는 어노테이션을 추가하여 스프링 컨테이너가 객체를 생성, 인식하고 관리(스프링 Bean으로 등록)할 수 있도록 한다.

- `@Controller`
- `@Service`
- `@Repository`

## 자동 의존관계 설정

컨트롤러, 서비스, 리포지토리를 `@Autowired`로 연결하여 의존성을 주입한다.

## 싱글톤(Singleton) 패턴

- new 키워드로 매번 인스턴스를 생성하는 대신, 스프링 컨테이너에 하나만 등록하여 공유 및 재사용한다.

- 메모리를 절약할 수 있다.

## 개요
정형화된 코드는 컴포넌트 스캔을, **상황에 따라 구현 클래스를 변경**해야 할 때는 **자바 코드로 직접 빈을 등록**하는 방법을 사용한다.

## 자바 코드로 스프링 빈 등록 방법
@Configuration 가 붙은 설정 파일에서 @Bean을 사용해 MemberService와 MemberRepository를 스프링 빈으로 직접 등록한다.


## 의존성 주입(DI) 방식과 생성자 주입을 권장하는 이유
의존성 주입에는 3가지 방법(생성자 주입, 필드 주입, 세터 주입)이 있다. 이 중에서 생성자 주입을 권장한다. 애플리케이션 조립 시점에 한 번 설정되면 변경이 불가능한 생성자 주입이 가장 안정적이기 때문이다.

## 프로퍼티 방식 접근 원리
- Thymeleaf가 ${member.id}와 같이 데이터를 출력할 때, 필드에 직접 접근하는 것이 아니라 getId(), getName() 같은 메서드를 통해 값을 가져오는 **자바 프로퍼티 접근 방식**을 사용한다.

## 메모지 저장의 한계
- 현재 데이터가 메모리에만 저장되므로, 서버를 재시작하면 데이터가 사라진다.
- 따라서, **데이터베이스 연동**이 필요하다.

## 단위 테스트 vs 통합 테스트 비교

| 구분 | 단위 테스트 | 통합 테스트 |
| --- | --- | --- |
| **정의** | 외부 서버나 데이터베이스 없이 하나의 클래스나 메서드가 독립적으로 잘 동작하는지 가장 작은 단위로 검증하는 테스트 | 데이터베이스, 외부 API, 스프링 컨테이너까지 실제로 연동하여 결합 상태를 확인하는 테스트 |
| **실행 속도** | 빠른 실행(밀리초 단위) | 비교적 느림(초 단위) |
| **주요 목적** | 비즈니스 로직의 정확성 검증 | 데이터 흐름 및 컴포넌트 간 연동 검증 |

## 테스트 관련 어노테이션

**`@SpringBootTest`**: 스프링 컨테이너를 실행한다.

**`@Transactional`**: 테스트 후 데이터를 자동으로 롤백하여 DB 상태를 유지한다. 테스트를 반복해서 실행해도 이전 데이터의 영향 없이 항상 동일한 환경에서 테스트할 수 있다.

## ORM(Object Relational Mapping)

**ORM(Object Relational Mapping)**
- 객체와 관계형 데이터베이스의 테이블을 자동으로 매핑해 주는 기술로, 객체지향적인 방식으로 관계형 데이터베이스를 사용할 수 있게 한다.

- Java에서 사용하는 대표적인 ORM 기술로 **JPA**가 있으며, 대표적인 구현체로 `Hibernate`가 있다.

## JPA(Java Persistence API)의 필요성 및 특징

- 스프링 `JdbcTemplate`과 `MyBatis` 같은 기술은 JDBC 리포지토리 구현 시 발생하는 반복적인 코드를 대부분 제거해 주지만, SQL은 직접 작성해야 한다.
- `JPA`를 사용하면 기존의 반복적인 코드뿐만 아니라 기본적인 SQL 처리도 자동화할 수 있다.
- **패러다임 전환**: SQL과 데이터 중심의 설계 → 객체 중심의 설계
- 이를 통해 **개발 생산성을 크게 높일 수 있다.**

## JPQL을 이용한 객체 조회

- 이름이나 전체 회원 조회처럼 **PK 기반이 아닌 조건으로 조회**할 때는 `JPQL`을 사용한다.
- `JPQL`은 테이블이 아닌 **엔티티 객체를 대상으로 쿼리를 작성**한다.
- `setParameter`를 사용하여 동적인 값을 전달할 수 있다.

## Spring Data JPA

**Spring Data JPA**: 인터페이스만으로도 반복적인 데이터 접근 기능을 자동으로 제공한다.

## `JpaRepository` 활용

- `JpaRepository`를 상속한 인터페이스를 만들고 **엔티티 타입과 ID 타입**을 지정한다.
- 구현체를 자동으로 생성하고 **스프링 빈으로 등록**해 준다.
- 개발자는 해당 인터페이스를 의존성 주입받아 사용하면 된다.
- `save`, `findAll`, `count`, `delete`와 같은 기본적인 데이터 접근 기능이 제공된다.

## 메서드 이름을 이용한 쿼리 생성

- `findByName`, `findByEmail`처럼 **메서드 이름을 규칙에 맞게 작성**하면 조건에 맞는 쿼리가 자동으로 생성된다.

## 복잡한 쿼리 처리

- 복잡하거나 동적인 쿼리는 `QueryDSL`이나 **네이티브 SQL**을 활용할 수 있다.
- 필요에 따라 `JdbcTemplate`이나 `MyBatis` 같은 기술을 함께 사용할 수도 있다.
